# FB-0003: Stale project sweeper and health labels workflow

> **Track** `automation` · **Size** `m` · **Difficulty** `intermediate` · **Reward** `120 REP`
> **Status** `open` · **Claim TTL** 21 days · **Epic** —

---

## Summary

A sandbox repo accumulates abandoned projects — that's by design, and the README says so. But
"abandoned" and "active" currently look identical in the index. Build a scheduled workflow
that computes a health signal for every project from Git history and `fermata.json`, and
nudges stale ones toward an honest `status` without any human having to remember.

---

## Context

- **Why now:** `projects/INDEX.md` lists everything as equally alive. As the repo grows, that
  index becomes actively misleading, and the fix has to be automatic or it won't happen.
- **Philosophy constraint:** Fermata explicitly says *most projects won't grow, and that's
  fine.* This workflow must **not** punish inactivity or auto-archive anything. It surfaces
  reality; humans decide.
- **Prior art:** `scripts/organize.mjs` already walks projects, reads metadata, and writes
  indices. This extends that machinery rather than duplicating it.

---

## Scope

| What | Where |
| --- | --- |
| Health computation (last commit, status, README completeness) | `scripts/organize.mjs` or a new `scripts/health.mjs` |
| Scheduled workflow (weekly) | `.github/workflows/sweep.yml` |
| Health column / badge in the generated index | `scripts/organize.mjs` |
| A single rollup issue rather than per-project noise | workflow |

Suggested signal:

| Signal | Meaning |
| --- | --- |
| 🟢 fresh | commits in the last 90 days |
| 🟡 quiet | 90–365 days, `status` still `active` |
| ⚪ resting | >365 days, or `status` is `paused` |
| 🔴 mismatch | `status: "active"` but nothing in >365 days, **or** `status: "archived"` with no `archived_reason` |

---

## Out of scope

- **Never auto-changes a project's `status`.** Suggest only. This is a hard requirement, not a
  preference.
- Not deleting, archiving, or moving any project folder.
- Not opening an issue per project. One rollup issue per sweep, edited in place.
- Not touching the validation workflow.

---

## Acceptance criteria

- [ ] A weekly scheduled workflow runs the sweep and can also be triggered by
      `workflow_dispatch`.
- [ ] Health is computed per project from the last commit date touching that folder, plus its
      declared `status`, using the four-state signal above.
- [ ] `projects/INDEX.md` gains a health column, regenerated by the same run.
- [ ] Projects in the 🔴 mismatch state are collected into **one** rollup issue titled
      `Project health sweep — <date>`, which is edited in place on subsequent runs rather than
      duplicated.
- [ ] No project's `fermata.json` `status` field is ever written by the workflow — verified by
      the sweep run producing no diff to any `status` value.
- [ ] The sweep logic runs locally via `npm run health` (or `npm run organize -- --health`)
      with identical output to CI.

## Getting started

```bash
git clone https://github.com/ScottyVenable/fermata.git
cd fermata
node scripts/organize.mjs           # existing index generation
git log -1 --format=%cI -- projects/tools/ai/vivarium   # the core primitive
```

Files worth reading first:

- `scripts/organize.mjs` — `changedProjectDirs()` already shells out to git; extend that pattern.
- `.github/workflows/organize.yml` — the existing post-merge job, and the model for a scheduled one.
- `README.md` § Automation — the table your new event goes in.

Watch out: `actions/checkout` defaults to a shallow clone with no history, so `git log` will
return nothing useful. You need `fetch-depth: 0`.

## Notes

- Tone matters in the rollup issue. "These three projects say `active` but haven't moved in a
  year — want to mark them `paused`?" is right. Anything scolding is wrong.
- Consider whether health belongs in `fermata.json` as a cached field. The reviewer's opinion
  is that it does not — it's derived, and derived data in the source of truth goes stale.
